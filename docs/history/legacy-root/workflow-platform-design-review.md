# 可组合流程方案设计审查（2026-09-19）

> 审查对象：[可组合流程与项目记忆改造方案](./workflow-platform-refactor-plan.md)及[可组合流程抽象方案](./workflow-composition-proposal.md)。本审查只核对设计与当前 V1.0.0 合同，未实现代码或运行真实流程。以下“阻断”表示在这些合同定义并验证之前，不能宣称两个新流程可配置后可靠运行。

## 总体结论

方案的方向成立：Engine、Collection 是独立流程，复用编译器与底座；两条新流程能用同一组运行和记忆原语表达。原方案仍缺少若干**从静态计划走到实际执行**的合同，尤其是运行中分支、节点间结构化数据、记忆与 Authority 的跨存储提交，以及多仓库/多 Run 的权限和容量控制。已将这些补为改造方案的必需验收项。

| 优先级 | 缺口与当前依据 | 必需设计决定/验收 |
| --- | --- | --- |
| 阻断 | **运行中分支与节点输出**：当前 `feature.schema.json` 的 Feature 只接受 `agent-reasoning`，状态没有通用 `skipped`；`result.schema.json` 没有类型化节点输出字段。问答“记忆命中则回答，否则查源码”、文档流程的按来源扇出不能只靠当前静态 DAG 和自由文本结果实现。 | 定义版本化 Node Result/Artifact 端口及纯规划的有界 continuation：依据已验证结果确定性追加下一批 Feature/控制条件，每次扩展重新校验 DAG、权限和预算。不靠任意脚本表达条件，不把 Gate/Decision 伪装成 Agent Feature。 |
| 阻断 | **控制节点与等待**：现有 Lifecycle Plan 核心是 Feature 图、`stopCondition` 和最终 Gate 列表；Profile/Kernel 分别处理 Decision。方案中的“用户确认节点”和“独立复核节点”还没有统一的创建、等待、撤回、超时及恢复合同。 | 明确 Decision/Gate 是什么执行类别、何时产生请求、怎样记录结果，以及 Run 在等待用户时的可观察状态。关闭条件按已提交的当前版本 Decision/Gate 判定，不能仅凭 Agent Result。 |
| 阻断 | **记忆跨存储一致性**：Run Authority 与拟议 Memory Store 是两个写入域。若 Submission 已提交而记忆提交失败，或记忆已写而 Run 关闭失败，当前方案没有恢复顺序。 | 用绑定 `submissionDigest/planDigest/sourceManifestDigest` 的持久 Effect/Outbox 与幂等 Memory Receipt；先确保 Run 证据可审计，再提升记忆。崩溃后重放/核对未决写入，避免重复、孤儿记录和把失败答案提升为已确认知识。 |
| 阻断 | **跨 Run 资源与输出冲突**：`scheduleFeatures` 只看一个 Run 的 Feature 图；Instance Set 的 `maxParallel` 不足以防止两个 Run 写同一目录、同时占用同一仓库锁或超出模型/搜索服务配额。 | 增加项目/来源/输出/Provider 级准入与租约，跨 Run 冲突键、容量和公平调度；同一输出目标的两个实例必须串行、隔离或在发车前拒绝。 |
| 阻断 | **多源数据外发边界**：只读文件权限并不能决定是否允许把内容发给某个模型或宿主。共享记忆若引用受限源码，摘要也可能泄露实现细节。 | Source/Memory Record 带分类和来源权限；派生记录继承最严格来源限制，跨空间提升须显式脱敏及共享范围复核。Runtime、模型、工具的接收范围纳入预检和 Dispatch Grant；不合规则只做本地受限处理或阻断。 |
| 重要 | **Run 内记忆快照**：原方案固定每个 Dispatch 的命中，但同一 Run 的前后节点可能读到不同的共享空间版本，使分析依据漂移。 | Run 固定可读 Memory Space 修订与检索策略；本 Run 新产生的知识先作为有证据的 Run Artifact 流转，提升为共享记忆后只供后续 Run 使用。若确需刷新记忆，显式重基并形成新的 Plan/Run 与可审计关联 Receipt，不能借 ordinary resume 悄悄换上下文。 |
| 重要 | **多仓库一致性**：几个仓库没有天然原子快照；只记录各自 commit 仍可能组合出不兼容版本。 | Source Manifest 固定每个仓库的不可变 revision/工作树摘要、采集时间与兼容性约束；检索读取固定快照而不是移动分支头，产出前重验。如果无法证明来源组合兼容，答案/文档标记该限制或停止准出。 |
| 重要 | **流程/记忆版本启停**：已有方案说明 ID/摘要与回滚，但未规定 Workflow 安装、激活、撤销和 Schema 升级的原子边界。 | Registry 原子切换活动版本；旧 Run 固定旧定义继续审计/恢复，新 Run 只用活动版；模板、Memory Record、索引和 Git 导出各有兼容/迁移规则，迁移失败可回滚且不覆写原始记录。 |
| 重要 | **上报启动级故障**：现有 `h:report` 能绕开 Registry/Authority，但仍依赖有效的安装绑定。若绑定文件本身损坏，原方案的“仍可上报”不成立。 | 保留不依赖项目/流程目录的安装级维护入口，或明确将绑定损坏列为人工修复场景；入口只能使用安装时可信的 Control Root，不能通过扫描磁盘猜位置。 |
| 重要 | **Git 可移植性与恢复**：Git 导出默认不含原始 Evidence；换设备后记录可能只有断开的 `evidence:` 引用。Git 提交也不覆盖索引、Run Authority 或尚未导出的记忆。 | 区分知识同步与完整备份；导出清单说明可移植来源、缺失 Evidence 和验证状态。恢复索引可重建，缺失证据降级；完整灾难恢复另有受管备份/校验流程。 |
| 重要 | **“快速搭建”的证据**：只有“无需修改 Kernel”仍可能需要大量专用模板代码和人工集成。 | 用两个新样板记录新定义、复用模板、新增 Provider/模板、合同测试与人工步骤；另测记忆命中后的读取量、错误复用率和来源漂移检出率。达不到低成本目标时回到通用合同而非塞业务分支。 |

## 建议的封口顺序

1. 先冻结类型化节点数据、Decision/Gate 控制节点、有界分支与全局准入合同；它们直接决定两条新流程是否能运行。
2. 再冻结 Source Manifest 的固定快照、外发权限、Memory Space 快照与跨存储 Outbox；它们决定记忆能否安全复用。
3. 最后执行 Engine/Collection 等价迁移和两个新样板，覆盖崩溃恢复、撤权、并发冲突、版本切换和 Git 导入。对照通过后才能把“新流程只靠配置快速搭建”作为能力结论。

本审查不要求把所有节点做成通用代码执行器。新节点只能使用受批准的模板/Provider；如果某个业务规则无法声明，应以版本化 Extension 显式实现和验证，不能把任意脚本藏入 Workflow Definition。
