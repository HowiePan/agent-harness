# 协调、验收登记与正式续接

本合同将用户目标、一次协调进程、一次原生派发和一次结果登记分别标识。恢复只能承接原项目、原目标、原合同及原计数；不因更换进程、Run 或错误类别得到新的权限。

协调器异常同样适用[基于事实的流程内恢复](action-recovery.md)。错误码只是诊断线索；是否继续由实际核验、操作语义、已有回执和有限恢复结果决定。未经执行的固定说明不能记为已尝试，未知异常不能仅因缺少专用处理器而直接退出。

当前持续执行采用 `task-repetition/1`：没有跨任务累计的协调、诊断、修复或复验总额度；成功恢复不会耗尽命令余额。次数只用于识别同一任务相同策略、关键输入和失败结果的连续无效重复。旧历史保留，不再用总次数阻断。本文后续“最多两次恢复”仅指同一登记阶段或命令动作的无进展重复，不是整个用户命令的总次数。诊断纠错独立计量；已有项目内材料缺少登记时可进入来源绑定的输入准备，保留全部原验收。

## 用户声明：命令发起与流程内续接

2026-11-07 用户明确：用户可以发起实施命令或其他命令；发出后允许流程内有界续接，并可放宽续接条件；严禁 Agent 或 Harness 私自发起命令，以免形成无限循环。本声明优先于此前“已有目标授权即可独立自动续接”的描述。

命令发起权仅属用户。允许当前命令内、原项目/目标/合同/权限下的有界修复、重试、重接及原定后续批次调度。构建测试、合法子 Agent 派发和 Kernel 幂等事务是内部步骤，不等于新的生命周期命令；内部步骤不能承载额外目标或扩大权限。

禁止自行发送 implement、amend、replan、quality 等新生命周期命令，也禁止以 CLI、脚本、API、恢复凭据或替代 Run 执行等价启动。历史实施指令、已批准版本计划、迁移回执和未完成状态均不构成本次命令的有效发起证明。维护/整改 Harness、准备恢复及说明计划，不授权恢复或实施业务项目。

续接须证明仍属于用户本次发起、尚未停止或终结的命令，保留原失败/进展/协调恢复计数，并有可信处理能力。相同失败或持续无进展达到有限策略上限即停止；换进程、Run、错误名称或内部 ID 不刷新额度。进程中断先收束效果；缺少可验证的当前命令上下文时，只完成已授权的诊断与恢复准备，等待用户明确发起命令。用户停止具有最高优先级，不能由自动恢复清除。

## 分阶段登记

`result-registration/1` 是控制根内的非权威进度记录。每次操作固定项目、Run、Dispatch、Epoch/Generation、packet、原生结果、命令、合同、源码及制品/策略/插件摘要。记录只保存阶段和内容寻址的 Evidence 引用，不保存另一份可修改的完成结论。

顺序为 `observed → prechecked → verified → submitted`。`verified` 表示验证结果已记录，结果仍可能失败；只有 Kernel Submission 和原 Profile 接受后才完成。先核验结果及依赖返修登记条件，再执行昂贵的 Host 检查；最终事务仍重新核验当前条件。

同一操作在验证后中断，必须重新核验原 Host Evidence、当前源码、绑定、停止状态和合同，然后从待登记阶段续接。其回执属于同一原始验证操作，不是允许跨派发复用旧绿灯。新 Dispatch、源码变化、不同结果或新鲜度要求均重新判定，不提升旧完成。每次源码、输出及工具输入漂移继续按原检查合同拒绝。

提交成功但确认丢失时，通过原幂等命令、Submission 和原生操作 Evidence 核对，补齐投影或审批制品，不再次派发或登记。相同命令换内容拒绝。登记操作使用独占锁；锁的年龄不能证明持有进程死亡。

`recordResultContinuously` 只在已存在验证记录、来源未变、没有停止/冻结、证据完整时保留原操作进行有限协调重试。次数写入同一进度记录，跨进程保留，默认最多两次恢复；它不增加业务开发额度。未验证阶段的未知异常先诊断，不盲重跑；同一持续故障耗尽后保留现场进入独立维护。

## 故障与交接

`execution-fault/1` 记录控制面实际失败阶段、来源、证据、下一动作及影响范围。未知错误进入受限诊断，不凭错误名称猜权限。结果校验器以进程内能力标记可更正交接；Agent 的同名错误码或 JSON 字段不能伪造该能力。新 Host 失败回执保存结构化恢复操作；原生结果 Evidence 保存检查引用，旧文本引用只用于已登记历史的兼容读取。

交接更正保留源码及完整原任务，只修正结果；不得为满足登记制造一次额外代码变化。原生结果保持不变，更正另行关联。下游义务可在 observations 说明，不产生其完成信用；本批次尚缺前置条件必须报 blocked，不能混入 verification-ready。

返修只重开唯一登记依赖，并失效它实际已完成的传递消费者。逐项保留旧完成 Submission、合同和计数，为消费者安排原合同的新鲜检查；未受影响任务保留完成。歧义或合同变化不能自动放行。恢复承接允许图中独立完成，要求每个保留完成仍有已完成依赖。

## 当前命令内的有界续接

正式恢复必须服从上面的命令边界。`visible-development-recovery.mjs` 和 `continueVisibleLifecyclePlan` 不能作为从普通维护对话自主启动业务的入口。准备模式不得创建业务派发或运行业务 Gate；是否允许改变恢复准备状态，还须遵守用户本次明确范围和停止标记。

R01/R02 已把该边界落实到代码。独立恢复脚本默认拒绝执行，准备/退休不运行预检、业务 Gate 或替代 Run。SDK 的预检、生命周期执行、原始 Run 创建、派发、启动、绑定、结果检查和 Gate 均要求当前命令上下文。`lifecycle-continuation/1` 还须证明属于同一上下文及核验封存的替代计划，旧回执本身不授予启动权。

可信嵌入宿主通过 `createLifecycleCommandHost` 核验原始用户事件；`withUserLifecycleCommand` 在回调内建立不可由普通 JSON 伪造的进程内上下文。Codex 宿主只读取精确 Session/工作区绑定的原生日志，匹配最近用户命令、项目别名的登记配置、Workflow、动作、目标和参数，忽略工具输出中的命令。初次观察最多取末尾 32 MiB，之后以 64 KiB 流式增量读取，单帧上限 8 MiB；分帧写入只作两次短观察重试，不整份载入历史。

控制根中的 `lifecycle-command/1` 登记把同一原生用户事件只接纳一次。回调结束即撤销上下文；用户停止、新生命周期命令、证据失效和恢复耗尽均拒绝继续。状态问询不视为停止，活跃上下文不因累计时长失效。原始命令 ID/引用仅是审计元数据，不能反序列化成执行能力。内部执行重入与封存承接共用默认两次协调恢复上限；它不削减正常批次和已有业务问题策略的额度，也不以更换 Run、错误名或命令后缀刷新。

唯一允许的跨进程例外是原可信宿主确认的 Run 创建前捕获子进程 EPERM 探测失败：须没有 Run/Host 效果，保留同一用户事件、意图、计划合同及计数，最多重启一次。普通错误标签不能取得该能力；其余退出只作准备并等待用户命令。宿主适配器是可信控制面边界，不是对能够修改宿主实现或控制根记录的本机程序的文件系统沙箱。

合法的内部承接仍须核验原生 Host、效果收束和当前 ExecutionReadinessReport。H4 禁止注入活动 Run。维护、判级和迁移不自行赋予业务启动权；恢复再次中断时也不得靠新发命令绕过上限。独占进度中的 started 仅是预留，不能据此等待不存在的 Agent。

承接事件以 `partialSubmissionIds` 明确区分获核验的实现进展与仅保留的失败/诊断上下文。后续迁移只能沿原封存条目核验，不能把 attempt 历史中的每条 Submission 升级为进展。旧事件缺少该字段时只检查原未完成前沿的当前提交，并继续核验父 Authority 的精确条目；其他历史保留但不获得信用。消费者等待返修时，可执行的依赖或独立任务先推进，消费者不因此解除阻断。

## 停止与验证

### 分问题处置与证据发现

诊断可以用 `resolutionActions` 分别声明 `dependency-repair`、`input-discovery` 和 `blocked`。一个未决历史输入不阻止同一原命令内先修复已有依赖；全批验收仍须满足所有原条件。依赖返修必须绑定原图直接依赖的 Feature ID、合同摘要、当前源码证据和精确修复路径，由 Kernel 核验项目硬边界、权威完成引用、预算、停止状态及消费者失效范围。Feature 目录参考不替代语义 owner 身份；旧式 scope 返修保留兼容，旧混合自然语言诊断先在原有限额度内补结构化澄清，不猜 owner 或重写旧诊断。

输入发现先使用精确项目内源库存及目录做有界只读调查，不下载、不扫描外部或控制根、不生成历史替代品。待调查动作由同一协调器安排只读澄清；查不到时标记 `unavailable` 并保留阻塞。找到输入时，Host 只接受源快照绑定的 `verification-input-catalog/1` JSON：`inputs` 中逐项声明项目相对 `path`、`sha256`、`version`、`purpose`。Host 重验目录和输入哈希、无链接路径及项目范围；每目录不超过 1 MiB，最多 16 目录、32 输入，输入流式核验累计不超过 32 MiB，超过则保持阻塞并要求精确分片。未知目录格式不能凭模型判断升级为可信输入。

被核验的发现通过当前接受评估生成 `verified-input-discovery` 上下文，始终 `completionCredit:false`；它只供原消费者完成历史语义及新鲜检查，不宣称历史兼容性通过，也不能消除未关联的授权或合同边界。外部问题须以 `actionId` 关联具体发现项，其他前置条件继续独立保留。依赖修复后如还有未决条件，消费者继续 blocked，由新源码上的有界诊断处理下一动作，不浪费一次实现尝试。共享依赖的真实已完成消费者仍须按原合同重新验证。

正式维护承接保留已绑定的混合阻塞诊断、澄清预留、原实现合同和计数；不得通过新 Run 刷新恢复额度。已核验的未决前置条件报告为 `prerequisite / resolve-recorded-prerequisites`，不能仅因已有一次诊断就误报没有开发进展。原生用户命令仍是唯一发起权；维护只能验证、迁移及封存准备，不能执行返修派发或业务 Gate。

用户停止、跨项目、未获授权的受保护效果、实质合同变化、无法排除的身份/证据冲突和资源保护继续阻断。长时间仍有已验证进展不按时长结束。spawn 预留、结果返回、验证运行和等待登记必须分别观察，不能将预留解释为进程已启动。

验收使用真实确定性检查及受控故障：验证前后中断、提交确认丢失、交接更正、依赖失效、恢复预留中断、重复结果、源码漂移、用户停止、长任务和资源保护。必须证明原检查未被削弱、有效工作未丢失、没有重复 Submission/派发，以及恢复后确实推进下一任务。维护夹具不等于真实业务版本验收完成。

## 用户重新发起后的正式恢复（2026-11-07 补齐）

整改与绑定成功不等于业务 Run 已可续接。准备阶段须核验并收束原生 Host Effect、保护工作区来源、按 H0–H4 退役不兼容 Run 并封存唯一替代计划；不创建替代 Run、不运行原验收、不解除停止。当前事故的接收者已由原生观察确认 interrupted，效果正式 contained，工作区相对原派发快照没有新增漂移。

只有下一条原生用户命令，且其时间晚于停止 Decision、项目/目标/Workflow/合同一致，才允许正式恢复。命令运行时对同身份的已绑定旧 Lease 先做有界收束、ordinary resume 和必要草稿来源保存，停止标记仍保留；身份已变则先走 source-link 正式承接。未知效果、未绑定派发、冻结、预算或合同边界不由恢复绕过。

预检通过后，`startLifecyclePlan` 为同 Run 或承接后的新 Run 记录精确 `resume-execution` Decision，绑定本次用户命令引用、时间、原停止 Decision、源码、Plan 和 prior Authority。维护请求、旧时间戳、伪造上下文或活动效果都不能获得这个能力。历史停止记录保留；当前门禁读取最新有效停止状态，不能把已经正式恢复的历史 stop 继续当成当前停机。原验收、失败/诊断计数及完成证据保持原规则。

隔离用例覆盖空闲停止和仍有 Lease 两类恢复，均真实完成原派发的检查及后续批次；同时拒绝维护、旧命令、活动效果、冻结、目标和 Plan 漂移。正式可实施结论须另有本次 `.tmp/continuous-maintenance/resume-ready.json`，明确替代计划未启动、第一未完成批次及剩余正常预检义务，不能只引用上一轮代码回归。

## 启动准备与用户命令入场（2026-11-07 补齐）

绑定 Session 的新 Hook 凭据使用 `admissionPolicy=native-current-command/1`，不设置按准备耗时失效的 `expiresAt`。它仍是摘要绑定的路由数据，不是可重放的执行授权。Coordinator 必须从精确 Session/工作区的原生日志核验最近用户消息、命令参数、登记配置和凭据签发时对应的用户事件；随后先一次性登记，再进入绑定检查、扩展加载和计划准备。若绑定核验期间用户停止或改发命令，重新观察后拒绝入场。

准备阶段和 Harness 共用同一个不可由 JSON 构造的命令边界，并核验 Authority 根相同。初次登记等待结束后还须重查活跃状态；准备出错也保留已消费记录，不能换进程重新发车。没有短时限不等于允许历史命令：维护消息、较晚的同文命令、来源缺失、停止、替代指令和已消费事件均拒绝。原生事件与 Hook 签发时间的关联窗口用于辨别原始事件，不限制从签发到启动所花的时间。

未声明新策略的旧格式凭据仍保留原到期规则，不能修改摘要、延长期限或升级过期凭据。单次可信 prestart EPERM 重试仍受原条件及持久计数限制。ExecutionReadinessReport 仍须在实际启动时新鲜有效；资源保护、业务预算、合同及用户独占发令权不变。
