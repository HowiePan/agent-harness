# 适中批次规划与原生执行

`bounded-delivery/2` 是可复用的 Delivery Lifecycle 策略。项目通过 `policy.deliveryBatchPolicy` 启用新计划校验；Engine 新生成的 Descriptor 默认启用。已有不可变计划继续保持原策略，只有经过审查和人工批准的 Plan/Amend 才启用新语义。该策略不要求一次派发完成某个百分比。

## 规划合同

业务 Feature 声明 `deliveryPolicy: "bounded-delivery/2"`、`deliveryBatchReserve` 和 `deliveryBatches`。计划批次与至少一个修复/集成预留合计不超过 20；放不下就提出有界 Feature 拆分，不能把大包改名为一个批次。每批的工作量以合理会话容量评估，超过容量拒绝；估计不足容量四分之一时必须给出独立隔离的具体原因，不得填充工作。数值是审查依据，不能替代审查人的源代码与完整交付成本评估。

每批声明 `id`、`phase`、`objective`、`dependsOn`、`allowedPaths`、`writePaths`、`obligationIds`、`acceptance`、`verification`、`sizing`、`checks`。`sizing` 包含 `basis/cohesion/estimatedUnits/capacityUnits/reserve`，必要时补 `smallBatchReason`。`phase` 为 development、acceptance、source-exit、verification 或 convergence。

`obligationIds` 对应摘要固定输入产生的合同、验证、聚合证书、最后源码退出四类义务。物化时验证精确覆盖、唯一批次 owner、完整依赖及检查覆盖。普通项目没有迁移库存时仍按实际合同/验证产生义务，不需要伪造证书。拆分子 Feature 用 `deliveryObligationIds` 选择原生产者的真实义务，同时保留自身合同/验证；原库存生产者和声明身份不改写，原 Feature 仍是全部原验收的汇合点。

固定输入中的完全相同义务使用同一稳定 ID 和一个执行 owner，`sourceOccurrences` 保留原提案、解析后的集合位置及合同引用；原合同数组和文档摘要保持不变。相同 ID 的语义内容不同则拒绝，不能用去重隐藏不同证书或退出要求。此归一化仅用于有界批次，旧计划继续保持原义务投影。

若 Amend 草稿因范围阻断停下，经过可信重新绑定的 Harness 运行制品发生变化时，同一命令可创建新的规划 Run：精确绑定旧草稿 Authority、原请求、原范围、批准基底和新制品摘要，复核已提交草稿文件及实施来源链。支持文件变化不触发替换，活动 Agent、已接受结果或未声明文件变化仍阻断；修复不自动发起 Amend 或转移人工批准。

实施基线若来自最后一次已提交输出，重试沿用并复验已固定的输出快照和原 Submission/Evidence，不从含有草稿文件的当前目录重建。草稿文件只接受已提交的精确字节；额外文件或实现来源漂移继续阻断。

`checks` 每项声明 `id`、`executionClass: "deterministic-process"`、`command: [executable,...args]`、完整 `inputs`、`outputs`、`covers`、`environment`、`cacheable`。缓存还要求 `toolchainFiles` 列出实际工具链文件；版本标签或启动代理文件不能代替真实编译器/解释器。不能证明完整输入或工具链时设 `cacheable:false`。检查只能运行确定性构建/测试/验证，不能借此启动 Agent CLI。所有修改证明输入的批次必须先于该证明。唯一 convergence 依赖其余全部批次，自己的检查强制新验。

## 执行与证据

编译器把计划批次降为独立的原生 Agent Feature，稳定原 Feature 的最终收口 ID、预算根和下游依赖。未依赖且无路径/合同/资源冲突的单元才可能并行，并且受 Descriptor 和宿主的限制；共享工作区不授予隔离工作树权限。完整批次可正常交接给下一原生 Agent；同一批内仍要交付连贯目标，不能逐个文件或证书退回。失败、中断和修复留在相应批次，沿用有界预算。

同一批准批次连续三次主动返回 `implementation-incomplete` 的零散交付，会保留源码/证据并要求有界的规模或执行策略复核，阻止再次盲目续发。真实 Host 检查失败、外部阻断、provider 中断和旧计划历史不计入这项碎片交付判断，继续使用各自的修复、恢复和预算规则；不因普通失败强迫 Replan。

派发包只展开本批义务和开发目标，完整批准数据通过固定引用与集合摘要保留，避免每个 Agent 反复读取全库存。部分批次完成不记为原 Feature 完成，也不进入原提案的完成继承集合。后续修订保留同一预算根的已完成批次检查点及实际 Submission/Evidence。

Agent 声称完成后，Application 按批准命令执行真实检查并封存 Host 回执。检查失败会保留原生报告，派生为未完成结果并移除失败检查覆盖的完成声明；环境失败单独阻断。执行过程保持原 Lease 的心跳并输出检查进展。检查改写来源源码时拒绝接受，不能把污染后的结果当作通过。

成功缓存同时绑定命令、完整输入、输出、脚本、真实工具链文件、环境、策略和制品。相关变化使缓存失效；无关来源变化可复用已验证输入的成功回执。收口再次核对上游所有义务的当前证明，复跑失效检查并运行新鲜的收口检查；版本最终 Gate 继续保留。

预算从摘要固定的真实 Authority 读取并转移实际计数、记录和原始未完成 Submission，拒绝活动来源、过期来源、根错配和更新后的历史回退。拆分子单元共享额度，耗尽时全部停止；增额必须另行绑定精确预算提案和人工批准。历史元数据不能代替计数承接，完成批次也不产生免费重试。

## 通用场景验收范围

“约 90%”是面向后续开发场景的适用性目标；有限场景目录不能证明未来真实项目的统计覆盖率，也不能用于压缩批次。当前可执行回归与边界目录如下，回归入口为 `node scripts/run-tests.mjs all`，聚焦用 `node --test test/delivery-batch*.test.mjs test/attempt-carryover.test.mjs`（支持通配的宿主也可逐文件传入）。

| 场景 | 机制与回归 |
|---|---|
| 新能力、接收端与消费者 | `delivery-batch-results` 真实源修改与行为执行 |
| 多批次完整交付 | `delivery-batch-visible` 原生可见适配器分批派发及真实检查 |
| 跨模块/共享接收文件 | `delivery-batch-scenarios` 固定义务组，不因共享文件合成大包 |
| 聚合证明、成员与来源继承 | `delivery-batch-scenarios` 子提案选择原生产者的精确证书 |
| 旧源码退出与跨边界前置条件 | `implementation-continuation` 固定生命周期与 requiredBefore，独立本地工作不被外部条件整体阻断 |
| 合同/验证收口 | `delivery-batch-results` 原合同保持、缺项拒绝、上游当前证据与强制新验 |
| 过大 Feature、预留不足 | `delivery-batches` 总批次含预留上界拒绝 |
| 大包、小包与隔离例外 | `delivery-batches` 容量上界、过小理由与完整目标 |
| 依赖环、缺失生产者 | `delivery-batches` 图与证明输入顺序拒绝 |
| 独立并发、路径冲突 | `delivery-batch-scenarios` 调度图并发与重叠串行；受宿主能力约束 |
| 重复通过、配置变化 | `delivery-batches` / `delivery-batch-scenarios` 真实缓存命中与失效 |
| 脚本、输出、工具链变化 | `delivery-batch-scenarios` 输入指纹失效与复验 |
| 检查失败、范围内修复 | `delivery-batch-results` 拒绝虚假完成、同批修复及预算保留 |
| 缺失环境、外部等待 | `delivery-batch-scenarios` 环境失败回执；`implementation-continuation` 外部作用域 |
| 长时间检查 | `delivery-batch-scenarios` 实际 Lease 续心跳，检查结束前不提交 |
| 网络/上下文/宿主中断 | `implementation-continuation` / `development-run-recovery-progress` 原回执和进度保全、受控续接 |
| 修订后预算继承 | `attempt-carryover` 实际计数、原 Submission、耗尽阻断及独立增额 |
| 后续版本 | `delivery-batch-scenarios` 同策略编译不同版本，无版本分支 |
| 性能矩阵、整体验证 | 作为批准的 deterministic-process 检查和最终 Gate；本次不运行下游业务性能矩阵、不宣称其通过 |
| 跨项目消费者、权限与批准 | 只调度本项目，保留外部回执和独立授权；不能借拆分扩大 allowedPaths |

新增工具链的深层动态输入、必须同时改写同一工作区的并行任务、跨项目原子提交等场景需要适配或采用串行/外部交接。无法证明证据复用条件时重验，不能用覆盖率目标取消保护。现有真实 Run 在用户批准新计划前保持原合同，不因本次框架测试而声称业务验收完成。

## H4 后只准备修订

旧实施 Run 闲置且接下来应 Amend 时，使用 `dev migrate --manifest <manifest> --run <old-run> --for-amend <registered-change> --command-id <id>`。先只读核查未来策略、精确登记范围、批准基底、旧成果和允许的规划准备差异；随后通过 Kernel 的 `freeze-execution` Decision 冻结旧 Run，再按其新 revision 应用 H4 绑定。源码、提交和预算不变，不创建生命周期 Run、不启动实施。失败后保持冻结，不回退为旧策略执行。重新只读检查 Amend 后，仍由用户发送正式命令。

## 批准前核验旧源码退出

Plan 和 Amend 应从当前源码追到替代实现、仍在使用旧接口的生产或测试入口、接收方及原验收命令。尤其要核对命令实际编译和运行的范围。早期检查可以按其依赖聚焦，原全范围验收须在前置能力齐备后执行。

退出批次或承担退出的收口批次用 `sourceExits` 记录精确退出路径、消费者清单引用 `inventoryRef`、先行检查 `beforeChecks` 和退出后新鲜检查 `afterChecks`。检查用 `{proposalId,batchId,checkId}` 引用。依赖其他项目内提案的检查用 `requiresProposals` 标出前置收口点。Harness 校验声明的归属、引用和顺序，独立审查核对真实消费者是否齐全、断言是否保留，以及下游是否已有可用接收路径。旧计划可读取，修订审查沿受影响的引用链核对仍有依赖的原计划部分。

## 统一中断策略（bounded-interruption/1）

项目经 H4 正式迁移到 `continuous-execution/1` 后，采用[按问题审核的处理周期](continuous-execution.md)，替代本节历史合同的逻辑根两次累计诊断上限；所有身份、权限、合同和验收边界保持。

本节的统一决策、受限诊断、处理与退出封装已实现。它不更改既有批准计划、预算或暂停条款；具体修复仍须有可信适配器，不能承诺任意工具或外部故障都能自动解决。新增问题先通过共同策略，不再以增加一个顶层错误码特例作为整改单位。本次规则适用于后续版本和其他开发项目。

### 两级停止与默认处理

“停止当前动作”用于隔离有风险或缺少证明的执行；“结束自动流程”才是向用户返回 `attention-required`。前者不自动导致后者。只读诊断、合法恢复及不依赖该条件的已授权工作仍可推进；没有新的执行授权时不能借诊断启动业务写入。

所有问题统一按以下顺序判定：检查必须停止的边界 → 收集缺失证据 → 选择原授权内的修复、恢复或策略复核 → 真实复验 → 继续。非硬性中断的问题必须先尝试有界的流程内解决；修复失败、能力确实缺失或控制预算耗尽后才能结束自动流程。未知错误也先进入受限诊断，不能默认为可写入重试或直接要求用户 Amend。

| 边界 | 必须停止的动作 | 流程内仍可处理的内容 | 何时必须交还用户 |
|---|---|---|---|
| 用户明确暂停、取消或变更目标 | 相应任务的进一步执行，按宿主协议收束活动效果 | 保全状态、记录已完成工作与未决效果 | 按用户指令结束或暂停，不擅自恢复 |
| 缺少授权、写入越界或受保护效果 | 未获授权的写入、发布、删除、权限扩张、跨项目操作 | 核实既有授权、收集证据、继续无依赖且已授权的工作 | 确认下一必要动作确实需要新增授权 |
| 绑定、Authority、来源、Lease 或证据身份无法信任 | 依赖该身份的执行与提交，禁止猜测归属或伪造回执 | 只读诊断；在独立维护边界内进行已有授权覆盖的修复与正式恢复 | 无法恢复可信身份、存在必须由人裁决的冲突或恢复需要额外授权 |
| 不可逆影响、并发冲突、数据或证据完整性风险 | 可能扩大影响的写入、重复外部效果及无证据完成声明 | 隔离、检查现有回执、幂等恢复、安全串行化 | 无法证明安全恢复，或安全恢复本身需要受保护操作 |
| 已批准执行预算或流程内恢复预算耗尽 | 继续消费该预算的执行，不重置计数、不换错误名获取新额度 | 封存进展、准备精确预算或策略提案；无关且合法的分支另按其预算判断 | 下一必要动作确需增额或当前授权恢复路径均已耗尽 |
| 必须改变批准合同 | 按未经批准的新合同实施，禁止降低验收或变更依赖前置条件 | 核实是否真有合同差异，准备最小修订及独立审查材料 | 确认改变需求、架构、范围、验收、批准批次结构或依赖合同确属必要 |

普通代码缺陷、测试/Gate 失败、工具或脚本问题、缓存失效、已授权路径修正、可恢复宿主/网络故障、上下文交接、规模估算变化和重复零散交付，都是流程内处理候选。候选不等于无限自动重试或扩大权限；实际行为仍须通过上述边界和证据检查。Gate 失败阻止准出，但有合法修复路径时不应直接结束整个实施流程。

### 有界解决与复核合同

统一决策器输入原始问题、权威 Run/Feature/Dispatch、原批准合同、有效权限、真实检查证据、来源身份、依赖图和预算历史；不凭 Agent 自报的错误名、严重性或“需要 Amend”结论决定退出。决策可为继续、受限诊断、局部修复、正式恢复、规模/策略复核、有界等待或请求用户介入。

规模复核必须区分：已存在实现、待开发内容、待验证内容和未知项。草稿未验收不产生完成信用，但可以减少重写成本；不能把全部原工作量照抄为剩余量。数值变化只触发复核，不能单凭重新估算就改合同或要求 Amend。复核后能在原批准批次内交付则继续；确需改变批准结构或触及计划明确限制时，准备最小修订。执行顺序、方法和聚焦验证可在原合同允许范围内调整，不得借此隐性拆分批准批次、压缩验收或形成超大单 Agent。

每次处理必须记录原因、适用边界、证据、选择的动作、额度和退出条件。恢复额度须有限，并受现有批准预算约束；诊断/复核额度明确记账，不能形成免费重试。实现时必须落实有限策略上限，不引入无法观测的后台等待。相同根因、相同来源与相同证据重复失败时不得原样重试；必须改变有依据的策略，或在合法路径耗尽后停止。根因身份不能随 failureClass、子 Agent、会话或 Run 改名而清零，正式来源承接保留相关历史。

外部等待必须有确切前置条件、可核验恢复信号和有限等待界限；等待期间只推进不依赖它的合法工作。没有可行独立工作且需要用户或外部主体提供新条件时，应给出具体缺口并结束本轮，不能无期限心跳。用户暂停优先于一切自动诊断/修复。

请求用户介入必须携带结构化依据：受阻的必要动作、必须停止的政策类别、原合同/授权引用、原始与复核证据、已尝试的处理及结果、累计预算、保留进展、无法在原边界解决的具体原因、最小所需决定。单独一句“任务过大”“无法继续”“请 Amend”不是合格的升级结果。

### 实现与验收范围

1. 盘点启动、派发、原生结果、真实验收、续接、最终 Gate、宿主故障和轮次上限的全部停止出口，建立出口到统一策略的覆盖表。
2. 在应用层实现版本化的统一决策和处理循环；中立 Kernel 保留 Authority、幂等事务与预算强制约束，项目/工具差异由适配器提供证据和修复能力。各入口消费同一决策结果，停止原因不再散落为互相冲突的错误码分支。
3. 接入现有路径修复、实现纠偏、规模审查、宿主恢复和 Gate 修复，保持批准合同、真实验收、适中批次、原生可见 Agent 和 H0–H4 规则。无法提供可信适配器时只能诊断或升级，不能回退到 Agent CLI。
4. 以端到端场景验证：范围内缺陷和 Gate 失败自动修复；新错误先诊断；估算过大自动复核；旧草稿减少重写但不冒充验收；一批完成后正常交接；真实上下文中断可恢复；外部前置只阻断依赖动作；同根因重复失败有界退出；跨 Run 不重置额度；不可信身份先隔离再正式恢复；越权/不可逆效果和耗尽预算不自动放行；确需改合同生成最小修订；用户暂停立即生效；未知严重性不能自动升级权限。
5. 同时检查“该继续却退出”与“该停止却继续”。每个停止出口都必须命中政策并给出证据；普通失败不能未经处理就落到通用 `blocked-dependencies` 返回。覆盖目标是常见开发场景的通用适用性，不设单批交付 90% 的强制指标，不把全部工作压进一个 Agent。

只有统一出口覆盖表、处理循环与上述正反向回归通过，并按实际补丁等级同步和准备正式续接后，才可宣称此项通用整改完成。当前 A10 容量阻断作为验收案例，不是唯一实现分支；本节本身不启动或恢复业务实施。

### 运行时实现与出口覆盖

| 出口族 | 统一入口与流程内处理 |
|---|---|
| 启动/预检 | `visible-lifecycle-events.mjs` 将真实 readiness 检查归入统一决策，并保留原阻断；未证明宿主或授权时不创建 Run |
| 派发/原生结果/验证失败 | `lifecycle-execution-service.mjs` 先通过统一策略选择有证据的现有修复器；无适配器匹配的已提交阻塞进入只读诊断 |
| 新问题、规模估算、零散交付 | `interruption-review.mjs` 生成 Kernel 预留的独立原生只读任务；明确已有实现、待开发、待验证和未知项，保留全部原合同 |
| 续接/崩溃/补丁承接 | 同一选择器识别未执行或待收束的诊断；Kernel 承接原任务、Submission/Evidence、诊断账本和停止标记，不发放新额度 |
| 最终/稳定 Gate | 两种协调模式均使用既有受限质量诊断、修复和新鲜 Gate；环境/超时失败先分类，不能伪造成源码 Finding；缺少该 Profile 的诊断能力或明确修复权限时保留证据升级 |
| Feature Gate/依赖阻塞 | 保留真实 Gate 回执、依赖图及可运行分支；已提交的任务阻塞可进入受限诊断。没有归属和修复适配器的 Gate 不会自动授予写权限，统一出口明确报告能力缺口 |
| 宿主/传输/例外 | 有原生中断完整回执且来源未变时可在原额度内恢复；缺少可信绑定时隔离依赖动作，记录受限控制诊断，仍须正式恢复，不能替换 Agent CLI |
| 准出/额度/未知退出 | `interruption-outcome.mjs` 封装必要动作、适用边界、尝试、证据、保留进展和最小所需决定；原有 Gate、审批及额度强制保护继续生效 |

`interruption-policy.mjs` 是应用层的共同决策器；Kernel `intervention.mjs` 只强制中立的只读预留、来源与额度约束，不包含项目策略。`execution-diagnostic` 没有源码写权限，最多一次尝试；同一原业务逻辑根全程最多预留两次，若原提案的修复预留更小则取更小值，并要求业务额度尚未耗尽。账本在派发前原子写入，重复的同根/来源/合同不会获得新诊断。失败的诊断作为审计保留，不能冒充原业务完成，也不会在原业务确实完成后永久占据业务准出条件；未关闭 Finding 和必需 Gate 始终保留。

诊断的 `in-scope` 建议须经当前源码 SHA-256、原 Submission、原合同摘要、路径及剩余容量检查。`unknowns` 区分正常范围内工作、待执行原验收、外部前置、合同变化和未解决问题；前两者须给出具体处理、保留的验证和已计入估算的成本，不能要求只读诊断先完成全部开发与验收。旧版未分类字符串不能自行解释为安全许可，须经受限澄清。成功只重开原批次并传入复核策略；原验收仍由实际 Host 检查决定。合同变化、外部前置及未解决结论保持阻断，系统不自动批准或发起 Amend。用户停止通过精确用户 Decision 保存在 Authority；自动修复不能清除它，恢复还要求原 Transport 已收束或正式恢复。

源码 `evidence` 只接受当前绑定库存及精确哈希；历史日志和排除产物放在独立 `observations`，只读取精确的项目内非链接文件（每份上限 1 MiB）并封存原始字节，明确不产生源码身份或验收信用。建议不合格时记录机器核验反馈，不把它误报成 Authority 丢失或直接抛出结束协调。允许的澄清必须引用确切旧诊断 Submission 和已验证 assessment，消耗原业务逻辑根同一个有限预留；同一诊断不能重复澄清，整个根仍最多两次且取原批准预留较小值。澄清失败或额度不足才有界停止，不能靠改名重诊断。核验、预留之间的崩溃可幂等续接；原结果永不改写。

### 协调者在进程退出后的责任

`coordination-recovery/1` 将命令、意图、Plan 和 Run 绑定到下一步处置，明确 `userGoalComplete`、`userInputRequired`、`processReplayAllowed` 和 `nextAction`。它是协调责任提示，不是新执行授权。异常退出不代表用户目标完成；普通异常先核查来源、保留证据和额度，确认 Harness 缺陷后在独立维护边界修复、验证、判级并准备正式恢复。只有确实需要批准、合同变化、增额，恢复额度已耗尽，或已有授权修复后仍缺少必要能力时，才请求最小用户动作。不得编造意图、直接重启退出的 Coordinator、手改 Authority，或等待没有启动的任务。官方恢复确实要求新 Hook 命令时，先完成全部修复、绑定和恢复准备，再请求一次该命令；“修到可实施”不等于批准发起实施。

只运行过辅助诊断的替代 Run 仍可承接原业务阻断：必须沿不可变 transfer 事件、原 Run Authority 摘要、封存的入站 Plan 和原 Submission/Evidence 核验，既不能要求制造一次新业务失败，也不能把复制历史或诊断完成提升为业务完成。

策略/Kernel/协调循环的变更属于 H4，必须走正式单 Run 迁移或闲置绑定重建，不能 `dev sync` 热注入旧执行。发布清单的本地重建只用于校验与测试，不代表发布、安装、切换或用户批准业务修订。

### 实现候选、Host 验证与恢复输入

新派发采用 Prompt 1.7 / 原生结果 1.3。`bounded-delivery/2` 批次可以提交 `verification-ready`：逐个批准义务提供 `implemented` 检查点和源码证据，`verificationRequest` 固定原批次摘要及按原顺序的检查 ID，不携带完成输出或未解除的阻断。应用层在验证 Lease 内执行原 Host 检查；全部新鲜回执通过才派生另一个 `completed` 结果，并重新验证 Schema 和 Profile。原生候选保留原样，Kernel 不接受未解析候选。检查失败保留真实回执并走既有分类、范围内修复及原额度，不能把尚未运行的检查填成成功。

派发前沿批准计划明确链接的 Authority 祖先逐条核验未接受草稿的原生结果、Host 身份、源码快照及 Evidence 摘要，生成不超过 256 KiB 的只读输入。只取最近的同逻辑根草稿，不扫描控制根或积累完整历史；草稿不产生完成信用。缺失、身份不符或损坏发生在 Agent 派发前，归 Harness 协调故障，不消耗一次业务尝试。输入路径、大小和 SHA-256 固定在 Dispatch，Agent 不得浏览相邻控制数据。

旧 `host-check-order-and-retirement-evidence-input` 阻断只能通过精确的 `delivery-coordination-review` 恢复：核验原提交、当前源码、原检查输入、新交接能力和真实退休草稿后封存能力回执，沿正式 H2/H3 部分进展承接重开同一前沿。其他外部审批、依赖和人工停止不能套用。恢复不改批准图、合同或历史失败；额度已经耗尽时，先生成精确增额提案并取得人工批准。一般流程内修复仍受原预算及每逻辑根最多两次诊断预留约束，不能承诺无限自动恢复。
