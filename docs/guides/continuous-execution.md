# 持续执行与有界恢复

`continuous-execution/1` 是显式选择的新执行策略。配置在项目 `harness.json` 的 `project.executionPolicy`，配置版本为 `1.2`。注册、H4 预览和新 Plan/Run/Dispatch 固定同一份策略；旧 Run 不热切换。未选择此策略的项目保留原预算和资源行为。

```json
{
  "version": "continuous-execution/1",
  "recovery": {
    "cyclesPerProblem": 3,
    "diagnosticsPerCycle": 2,
    "sameStrategyFailures": 2,
    "stagnantCycles": 3
  }
}
```

## 周期与停止

正常开发按批准的适中批次推进，不逐文件申请。预算不再限制任务终身提交次数。失败按稳定问题身份进入有限处理周期：问题身份由逻辑根、任务、验收和检查共同决定，不包含源码摘要、错误类别、Agent 或 Run。重命名错误不发放新额度。

每个无进展窗口默认最多三个失败周期，每周期最多一次独立只读诊断及一次必要澄清。诊断必须核验当前源码、原 Submission、完整合同、具体剩余工作和下一策略；普通确定性修复器可直接处理已验证故障，不额外派诊断 Agent。策略连续失败两次后，同一策略建议不能再重开原任务。三个周期仍无有效进展，或不同问题轮流出现但整体仍无推进时，停止自动恢复并提供处置依据。

已验证的独特实现进展仍按原 Profile、Evidence、来源防循环及 continuation 检查认定，绝不产生验收信用；它开启下一处理窗口，历史失败、进展及诊断记录完整保留。源码变化或重复绿灯本身不能使 continuation 通过。完成仍须完整 typed output、真实消费者、独立审查和当前最终 Gates。

用户停止、跨项目操作、未获授权的受保护效果、证据/来源身份冲突和实质合同变化优先阻断；内部审核不能放行这些边界。问题已经核验而没有可信修复能力时，提供精确缺口，不无限等待。

## 资源、输入和日志

辅助脚本仍走 `scripts/run-bounded-script.mjs --request <file>`。新策略的请求可选择 `resourceClass: helper|build|test|package`；默认 helper 512 MiB/4 进程，其他三类 2 GiB/16 进程。CPU 默认 25%，保留主机至少 20% 且至少 1 GiB 内存余量。无默认总时限。

额外资源必须提供 `policyBinding`，内容来自当前 packet 的 `scriptPolicyBinding`，再加该 packet 的 `packetDigest`。监督器从控制面的实际活动 Dispatch 读取配置；仅在请求里增加 limits、伪造摘要、使用已结束 Lease、只读任务或跨项目脚本均不能扩大权限。资源上调只能在已登记档位内，仍受机器余量检查；不能规避 Job 或清理机制。当前仍串行启动重型确定性进程，原生只读任务按依赖/冲突图使用宿主并发；项目写入保持单写者。

`inputMode: stream` 在有策略绑定时允许顺序检查较大精确库存，默认上限 65,536 文件/1 GiB。大量路径通过 `inputManifest` 引用精确清单文件，并把清单自身列入 `inputs`。清单每行是一个绝对路径 JSON 字符串，按不区分大小写的顺序严格排序、不重复、最后保留换行；监督器逐条读取和计量，拒绝超长行、链接及超额。它不允许整批载入或递归展开计划，也不构成文件访问沙箱；实际内存仍受 Job 限制。默认 bounded 模式保持 128 文件/32 MiB。

新策略将 stdout/stderr 同步分块落盘，避免内存队列。默认界面窗口 1 MiB、每次执行日志合计 64 MiB。显示截断不终止任务；磁盘日志超限或写入失败仍失败并清理后代。回执保存完整性标志、精确路径、字节数和 SHA-256。不能把不完整日志当完整证据。

## 修复、续接与迁移

原有环境诊断、输入绑定、Host 验收失败修复、原生中断收束及正式恢复共用同一周期策略。输入绑定允许从明确且唯一的构建目标清单证明旧路径的真实位置；只调整检查输入，不改原命令、验收、依赖或写入归属。歧义、链接、越界和来源漂移保持阻断。

`dependency-repair/1` 处理消费者发现已完成依赖仍有缺陷的返修：当前只读诊断、原阻塞 Submission 和已封存评估必须绑定同一源码与未变合同，修复路径必须全部归于唯一的直接登记依赖。重开该依赖的完整原批次，并对实际已完成的传递消费者安排保留原合同的新鲜复验；旧完成 Submission 作历史，原阻塞消费者等待依赖完成。不得从自然语言猜 owner、扩大验收或跨项目授权。歧义、来源冲突、用户停止或预算耗尽保持阻断。

返修使用已有额度和每问题有限周期，不新增失败额度，不清零历史。返修上下文作为精确摘要绑定的只读输入交付；生产方必须提交新的实现并重新经过原检查，随后才重开消费者，仍须新鲜执行其全部原检查。其他外部输入和受保护动作继续保留原边界。正式迁移保留诊断、阻塞前沿、返修状态和历史记录，不重复消费诊断额度。

若实现变更已被真实提交保留，但交接格式被拒绝，后续更正交接无需制造额外源码改动。完成登记须逐条核验返修起点之后、同一登记生产方的连续实现 Submission、原结果 Evidence 与前后源码库存，确认最终仍保留返修路径的实际差异；新的完成提交仍须通过原检查。`implementationSubmissionIds` 单独记录实现来源，`repairSubmissionId` 记录新完成提交。旧完成、断链、异主变更、缺失证据及已回退的修复均不能获得返修信用；失败记录和计数保持原样。

进程仍在时继续观察原会话；异常退出先收束 Host 效果，再按原授权使用正式恢复。缺少可信宿主重接时不能伪造返回或启动 Agent CLI。恢复能力不足时明确报告缺口，不能保证所有宿主/网络故障均可自动处理。

策略语义和 Kernel 账本变化属于 H4。正式迁移前封存旧配置原始字节、源码库存和 Authority。只允许增加 executionPolicy 与升级配置 Schema；其他配置或源码变化拒绝。配置源码桥不产生任何验收信用，不改原 Submission/失败计数/完成状态。之后通过 H4 预览、绑定和完整承接创建替代计划；新问题视图包含其真实旧失败，旧累计账本仍保留。首次未完成批次继续原合同，最终验收必须新鲜执行。

本策略不自动启动业务实施，也不授权提交、发布、删除、跨项目写入或提高机器资源硬上限。

只有用户本次发起的命令允许按[协调闭环合同](coordination-continuity.md)在流程内有界续接；禁止凭历史授权、独立恢复入口或 API 自主发起新流程。Harness 维护和准备就绪请求不授权业务实施。入口已要求宿主核验的当前命令上下文；登记断点、内部有限协调恢复和消费者失效范围也以该合同为准。
