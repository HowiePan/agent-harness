# Extension Contract

## Pack boundary

An Extension Pack may register:

- Profiles that define workflow eligibility, projection, and closure policy;
- plugin factories for Scheduler, Runtime, Model Router, Tool Broker, Codec, Gate, Artifact, Storage, or OS Sandbox;
- read-only legacy importers;
- a declarative `commandManifest` that maps project-neutral action tokens and presets to one Profile's scopes;
- build-time descriptor or Feature-graph operations.

The command manifest is versioned data, not a Codex prompt. Tool adapters accept the portable `h:<project-alias> <action> <target> [preset]` envelope; the project alias is external installation data and is resolved before the manifest. Provider, model, language, and build-system names stay out of the global router. Action aliases must be unique within one manifest. Every action declares a target kind, a default preset, and presets with an explicit scope and mutation flag. A parameterized preset may declare a fixed argument prefix and receives only the non-empty suffix as a selector.

Default Harness creation installs no provider-specific, consumer-specific, or legacy Extension Pack. Installations require an approved Authority Decision, register Extension entrypoints under the standalone control root, reject symlink/junction traversal, and bind a complete artifact-manifest digest in an installation receipt. Bundle every runtime dependency inside that artifact root and list every file. Projects bind the exact Harness and required Extension identities in their central Project Descriptor; run start fails when an ID, version, or digest is missing or mismatched.

Every production Project Descriptor explicitly declares `policy.agentExecutionMode` and `policy.promptCodecPlugin`; schema and Registry validation reject either omission. A Descriptor may use `policy.actionExecution.<action>` to select a different mode and Runtime for one lifecycle action, but it is allow-policy only: persisted execution authorization is forbidden. Core resolves it from the Command Intent and pins both fields into the Plan, Authority metadata, Dispatch, and Runtime Receipt checks. Every Dispatch pins the Prompt Codec ID/version and Prompt Contract version. The codec deterministically compiles the immutable packet into the complete child-Agent prompt and returns both packet and prompt digests. Operator and Runtime adapters transport that exact text and may not author or mutate its prose. `conversation-visible` is the interactive default: the selected Agent Runtime declares `user-visible` and `host-orchestrated`, has no `process.spawn` permission, and binds each Lease through a trusted host adapter. Its receipt binds `agentId`, `dispatchId`, `packetDigest`, `promptDigest`, Prompt Codec identity, and Prompt Contract version, contains `visibility.mode: user-visible`, a surface kind, and an inspectable task reference, and carries matching host attestation over both digests. Host-orchestrated visible Runtimes are driven by the current conversation through lifecycle start, Dispatch scheduling, exact generated-Prompt delegation, heartbeat, bind, and submit operations. Direct execution-plugin/Kernel bypasses are denied; missing Prompt compilation, host delegation, attestation, inspection, or fresh heartbeat is attention-required and cannot improvise a prompt or select a different Runtime. `headless` is explicit and never inferred: it additionally requires trusted deny-wins constraints and a host-verified command-scoped Grant derived from the original CI/unattended request. A process-capable Agent Runtime also requires a Core-issued per-launch capability, managed outputs, and sandbox enforcement. Process Gates require a live progress observer before launch.

A legacy importer is read-only and deterministic. Its assessment must satisfy the strict migration-manifest schema, identify the exact importer version, and bind every fact to an inventoried source-file digest. It must not follow or omit symbolic links or junctions, add undeclared fields, retain private mutable state, or treat a legacy completion string as current Authority. Capsule creation normalizes the staged logical root to `payload` and rejects any mismatch between the staged inventory and importer assessment. Extensions may declare replayability and effect classes but may not select a concrete Run or recovery mechanism; Core owns the `RunLineageResolution`. Verified control-root-only hard recovery uses a Core `RecoveryResolutionReceipt`, while publication, privilege expansion, irreversible external migration, deletion, and external cutover remain protected effects.

## Testing

Test manifest validation, denied permissions, immutable plugin envelopes, extension duplication, missing and mismatched identities, visible Runtime receipts, headless opt-in, rejection of process-backed interactive Agent execution, no-fallback host failure, output budgets, cleanup receipts, fail-closed sandbox behavior, and packaged resolution of every declared entry. Consumer Profile tests use synthetic fixtures and must not read legacy Harness source.

## Defect handling

Capture the Harness release digest, Extension identities, sanitized Descriptor digest, command, Authority revision, Dispatch and Evidence references, expected result, actual result, and a minimal synthetic reproduction. Fix the owning upstream layer, publish an immutable release, then update the Project Registry binding. Emergency testing may point to a reviewed commit artifact; it must not create a consumer-local fork.
