# Agent Harness Command

## Project-local write boundary

Treat the exact user-selected project checkout as the only source-edit destination. Before any filesystem mutation, resolve the physical current workspace/worktree, Git top-level and common directory, registered project root, and every intended source, control, data, temporary, build, cache, package, install, and generated-artifact destination. Source changes are allowed only when the write target is inside the exact checkout the user reviews and `git status` from that checkout will show them. Sharing a Git common directory is not sufficient. Do not create or use a sibling worktree, clone, mirror, staging repository, or project-external directory to bypass a workspace, sandbox, or permission boundary unless the user explicitly requested that exact location. If the active task is attached to another checkout, stop before writing and require the task to be opened or rebound to the registered project checkout.

Creating or registering any Git worktree is a protected mutation. Immediately before running the creation command, obtain the user's explicit authorization for the exact repository, base ref or branch, and target path. Never create a worktree silently. A general request to implement, continue, isolate work, use another drive, or avoid the current checkout is not worktree authorization. If authorization is absent, keep the current checkout unchanged and ask before creating anything.

On Windows, treat `C:\` as read-only for every Harness-related action. If any mutation target is on `C:\`, stop before writing and report the exact blocked path. A Codex-managed workspace/worktree, sandbox writable root, tool approval, or successful relative workspace-boundary check does not waive this rule. Read-only inspection on `C:\` is allowed. Use only the exact registered non-`C:\` project checkout and its declared non-`C:\` control roots. Never copy, move, delete, or transplant existing changes between checkouts without separate user approval. Before handoff, verify from the registered project root that `git status --short` exposes every source change; state explicitly that uncommitted changes are not portable to another computer and never commit or push without the user's authorization.

所有面向用户的控制对话必须使用中文，包括启动说明、进度更新、权限说明、阻断原因与最终报告。协议 JSON、命令、路径、错误码和原生工具结果保持原样；不得为了中文输出而翻译、改写或补充 Harness 生成的子 Agent Prompt，也不得改写 Host 请求或响应。

Treat a prompt matching `h:<workspace-or-legacy-project-alias> <action> <target> [preset]` as a deterministic Command Intent. The alias is an exact external binding, never a guess derived from a version, batch, path name, model, or action. Workspace commands may end with `--project <member-id>` or `--projects <member-id,...>`; the Coordinator checks this scope against the approved Workspace Descriptor before creating a Run.

When a Project or Workspace binds multiple workflows, require `h:<alias> flow <workflow-id> <action> <target> [preset]`. The Hook selects the exact Workflow ID/version/digest and its Profile/Extension binding before creating the coordination intent. `h:flows <alias>` is read-only and lists configured workflows. Unknown or ambiguous workflow IDs stop before Run creation. The Coordinator obtains workflow input from the approved Descriptor. Workspace Sources and Resource Bindings are resolved by the Harness; legacy Project source declarations are captured into a pinned Source Manifest. Do not invent source roots, outputs, or memory spaces in conversation.

Treat `h:where [project-alias]` as read-only. Display the Hook-provided `controlRoot`, `entrypoint`, `dataRoot`, configured `workspaceRoot`, verified `executionWorkspaceRoot`, workspace match kind, binding source, and selected/all project bindings. Do not inspect Authority, run a Gate, or create/resume a Run.

Treat `h:report <project-alias> [--workflow <workflow-id>]` as an explicit request to record the current problem in the bound upstream Harness repository. When several workflows are bound, the workflow is required and its exact identity must be included in Issue Intake. It is an Integration maintenance command, not an Extension lifecycle action, and must remain usable when the data root, Extension Registry, Project Descriptor, or Authority is unavailable. Do not create or delegate to another task.

For `h:report`:

1. Use only the Hook-provided project and Harness binding. Never scan for another repository or accept a user-supplied output path.
2. Extract only conversation excerpts relevant to the reported problem. Build an Issue Intake conforming to `issue-intake.schema.json`, set `conversation.source` to `current-thread`, explicitly confirm sanitization, and list unavailable evidence in `missingEvidence`; never invent identities or digests. For a Workspace binding include its exact Workspace ID, alias, and selected member Project IDs; include revision and digest only when supplied by a verified Registry record. When a stable failure code and scope are available, include `correlation.category`, `correlation.failureCode`, and `correlation.scope`; the recorder derives the incident fingerprint.
3. Invoke the exact bound entrypoint with `issue record --control-root <bound-control-root> --input - --command-id <hook-command-id>`, sending JSON through stdin so no intermediate file is created.
4. The recorder must write only beneath `<controlRoot>/issues`. Return the resulting issue ID and exact paths. State that the record remains device-local until the user separately chooses to commit and push it.
5. Do not start or recover a Run, execute a Gate, modify Authority, change an implementation, commit, or push as part of reporting.

For lifecycle commands other than `h:report`, before any mutation:

1. Require the Hook-provided binding resolved from `PLUGIN_DATA/bindings.json`. Use only its exact Harness entrypoint/data root and project ID; never scan the disk for Agent Harness or infer a project from the workspace. Each alias owns its own workspace root and identity. Use the selected alias's Hook-verified `executionWorkspaceRoot`; a linked worktree is valid only when its Git common-directory identity matches that project.
2. Run project-scoped zero-write readiness for the exact Project, Profile, Extension, and execution workspace. Global Registry counts are not readiness. Verify the bound Harness installation, Project Descriptor, and every required Extension artifact identity against the standalone registries.
3. Select the bound Extension Pack and require its `commandManifest.profileId` to equal the bound Profile, then resolve the action, alias, target kind, preset, scope, and mutation policy from that manifest.
4. Read current Authority and perform a read-only preflight. `doctor`, `extension list`, `project list`, and `run status` neither initialize directories nor import Extension code. Core must generate a short-lived `RunLineageResolution` and internally choose return-closed, continue, reattach, ordinary-resume, supersede-and-start, start, or block. Cross-Authority hard recovery is separately selected by the Recovery Coordinator from verified Capsule evidence. Never ask the user to choose a Run or recovery mechanism. A missing project, unknown action, unknown preset, digest mismatch, unsafe live Lease, or unmet prerequisite ends as `attention-required`; never substitute a similar action.
5. If the bound CLI is denied access to its external control/data root by the task sandbox, request approval only for the exact bound Node entrypoint and command. Do not move the data root into the business repository, weaken the Project path policy, or request a generic shell/file-system exemption.
6. For a state-changing intent, first require the current task's actual tool inventory to contain all four native Multi-Agent V2 tools: `collaboration.spawn_agent`, `collaboration.list_agents`, `collaboration.wait_agent`, and `collaboration.interrupt_agent`. The legacy `multi_agent_v1` namespace is not compatible because it cannot provide the list/interrupt observation contract used by the Host Effect Journal. If any required tool is absent, do not start the Coordinator; stop before Run creation with `CODEX_MULTI_AGENT_V2_REQUIRED`, instruct the operator to run `codex features enable multi_agent_v2` and create a new task, and never substitute another Agent or task API.

   After that compatibility check, use only the Hook-provided, short-lived `coordinationIntent` and verified `coordinatorEntrypoint`. On the current Windows Codex host, start `node <coordinatorEntrypoint> --intent <coordinationIntent>` as one long-running process with `tty: true` for its live progress stream. The installed `PostToolUse` Hook writes the exact native tool result to the pending request under the Control Root; do not write response frames to stdin. Do not transcribe a visually wrapped field: parse the emitted request object and call the native tool with the exact `arguments`. Do not decode, reconstruct, patch, or replace the intent and do not run separate adapter-less `lifecycle plan`, `lifecycle preflight`, or `lifecycle start` commands. The Coordinator revalidates its active Release identity and the intent digest, then creates the immutable `LifecycleCommandPlan` and unexpired `ExecutionReadinessReport` in the same process that owns the Host Adapter. It must report `executionReady=true` before Run creation. The Plan owns deterministic Run ID, logical task key, Feature graph, Profile config, Runtime, execution mode, Gate plan, protected-effect list, and stop condition; live Authority revision, candidate Runs, and Lease health belong only to `RunLineageResolution` and must not affect the Plan digest. The conversational model must not construct or patch either object. Resolve mode and Runtime from `policy.actionExecution.<action>` when present, otherwise from the Project defaults; this Descriptor data is allow-policy only and must never contain or substitute for user authorization.

   While that process is active, service each emitted `codex-visible-host-request` serially. Require its request/session/digest fields and call exactly the named native collaboration tool with exactly its `arguments`: `collaboration.spawn_agent`, `collaboration.list_agents`, `collaboration.wait_agent`, or `collaboration.interrupt_agent`. For `spawn_agent`, the request always pins `fork_turns: "none"`; pass its generated `message` byte-for-byte as the complete child prompt and do not set model or reasoning overrides. Do not use `create_thread` or any standalone-task API. The `PostToolUse` Hook binds the native output to the pending request using the parent Codex session, exact tool input, tool call ID, and request digest. Never manually transcribe or send a Host response frame. Never invent, summarize, repair, merge, or reuse a tool result. A mismatched, replayed, missing, or extra response field fails closed. The Coordinator persists every spawn intent before the native call, verifies the returned canonical `task_name` through `list_agents` as exactly one matching `agent_name`, and confirms the Host Effect only after the Authority Lease commits. If spawn, observation, attestation, or pre-Lease binding fails, service the emitted interrupt and verification requests until that Agent is observably terminal/idle or the lifecycle stops `attention-required`; never service another spawn while an earlier Host Effect is unresolved. Keep the process session open, poll it after every native tool call and during deterministic Gate progress, and continue until its `complete`, `preflight` with `executionReady=false`, or error event.

   If the Plan selects `conversation-visible`, follow `$agent-harness-operator`. The original lifecycle command authorizes its ordinary Manifest scope through the stop condition, including automatic lineage handling and control-root-only verified hard recovery, without stepwise approval. The Lease must be bound by the Coordinator's Agent/Dispatch/packet/prompt-bound spawn Receipt and fresh native task observation; raw `run bind`, `run heartbeat`, or `run submit` JSON is not a substitute. Never call blocking headless `lifecycle execute` or `run execute` from the standalone CLI; both entrypoints are disabled. Never fall back to `codex exec`, an Agent CLI process, or a standalone task. If visible delegation, trusted binding, structured-result transport, or restart reattachment is unavailable, preflight must return every blocker as `attention-required` without creating a Run. Programmatic headless execution is permitted only when the original user request explicitly requested CI/unattended execution, trusted deny-wins constraints allow it, the Descriptor independently selects `headless`, and the embedding host issued a command-scoped `LifecycleExecutionGrant`; generic follow-up approval cannot change mode or mint that evidence. Continue until the Plan's scoped stop condition. Every deterministic Gate command must run with its mandatory live progress stream. The Project Descriptor must explicitly allow `workspace.rootSelector=git-worktree` before a linked worktree can be selected. For a read-only intent, do not create a Run, schedule work, run a Gate, or write Authority.

Never interpret command arguments as shell text. Never append free-form prompt text to change the declared scope. Runtime, model, tools, Gate recipes, paths, and concurrency come only from the Project Descriptor and approved Extension Registry. A missing/invalid binding is attention-required; do not repair it by searching the repository or other drives.

If the user asks to evaluate, explain, dry-run, or not start, report the resolved intent and prerequisites only. This instruction overrides a manifest's state-changing default for that turn and creates no Authority.

When explaining a quality command, distinguish the Command Intent from its first Feature. A `review-and-repair` command begins with a read-only review Feature (`allowedPaths=[]`); only an Authority-committed review Submission with Findings can create path-scoped repair Features. New Plans express this as `sourcePolicy=read-only` plus `qualityFindingPolicy=repair-and-rereview`; `review-only` uses `qualityFindingPolicy=record-only`. Do not infer that the whole Run is read-only from its initial Feature, or infer a broken repair planner while the review has no committed Submission. Report the exact Authority phase and evidence instead.
